## External Signals (Researcher)

- Ultralytics supports the Python `YOLO("*.pt")`, `model.train(...)`, `model.val(...)`, and `model.predict(...)` workflow for object detection training, validation, and prediction.
- YOLO11 detection weights include `yolo11n.pt`, `yolo11s.pt`, `yolo11m.pt`, `yolo11l.pt`, and `yolo11x.pt`; Phase 2 uses `yolo11s.pt` as the preferred baseline while accepting smaller, larger, or custom `.pt` weights.
- Current Ultralytics docs increasingly show newer model names in examples, so the scripts should accept generic `.pt` model names rather than hard-code only one family.
- UAV/small-object training usually benefits from larger `imgsz` values, but this increases GPU memory needs. `close_mosaic` near the end of training is a practical default to stabilize final epochs.
- Prediction must remain generic visualization only: annotated images/videos are useful for false positive and false negative inspection, but this phase must not include tracking handoff, targeting, or deployment logic.

## Internal Health (Architect)

- The repo already had Phase 1 dataset preparation, validation, DVC docs, and a `data_v1.0.dvc` pointer.
- Phase 2 should stay as a separate CLI layer for experiments and reporting, not extend dataset-prep scripts into training orchestration.
- Training, validation, and prediction scripts should never modify `data/versions/*`; all outputs belong under `runs/` and `reports/`.
- Metrics parsing must tolerate Ultralytics `results.csv` schema differences and degrade gracefully when optional columns or plots are absent.
- The repo has `.agenteam/config.yaml` final verification set to `python3 -m pytest -v`, but there are still no tests. That should be addressed in a later quality phase.
